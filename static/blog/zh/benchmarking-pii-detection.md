## 评估设置

我们在一个包含 1,200 个标注样本的留出测试集上评估 PII Engineer，覆盖所有 13 种支持语言。每个样本包含 1-5 个 PII 实体，涉及 9 种支持类型。测试集在语言和实体类型上均衡分布，避免偏差。

评估使用严格的跨度匹配——实体边界和标签都必须正确才算真正例。部分重叠计为误报。

## 表现优异的类型

### 结构化模式（F1 > 0.95）

**电话号码**和**电子邮件地址**具有高度结构化的特征。NER 检测与后处理流水线中正则验证的结合实现了近乎完美的效果。模型学习上下文线索（"call me at"、"email:"、"电话"），流水线则验证格式。

### 政府证件（F1 > 0.92）

各国特定的证件格式（NRIC、NIK、CCCD、Aadhaar）具有独特模式。模型捕捉上下文线索（"IC number"、"CCCD số"、"NIK"），验证阶段检查格式合规性。

## 模型的薄弱环节

### 人名（F1 = 0.823）

人名是最难检测的实体类型。常见失败模式：

- **边界错误：** "Dr. Sarah Lim" 被检测为完整跨度而非仅 "Sarah Lim"。规范化阶段处理常见前缀，但不常见的头衔或敬称可能仍被保留。
- **常见词误判为人名：** "Joy"（情感 vs 人名）、"Will"（情态动词 vs 人名）、"May"（月份 vs 人名）。上下文通常能消歧，但短句缺乏信号。
- **音译人名：** 同一个中文名字可以有多种罗马化拼写（Xiao Ming / Siau Beng / Tiểu Minh）。模型通过多语言训练数据处理此问题。

### 护照号码（F1 = 0.810）

护照号码看起来像随机字母数字字符串——容易与参考编号、订单号或序列号混淆。模型高度依赖上下文（"passport"、"travel document"），验证阶段拒绝纯数字的候选项。

### 车牌号（F1 = 0.842）

车牌格式因国家差异极大（SG: SBA1234A, MY: WKN5678, VN: 51A-12345, ID: B1234ABC）。模型能处理大多数格式，但偶尔会将短字母数字代码误分类为车牌。

## 流水线效果

8 阶段后处理流水线显著提升了原始 NER 输出。以下是各阶段相对于原始模型输出的 F1 增量：

| 阶段 | ΔF1 | 主要效果 |
|------|-----|----------|
| Reclassify | +0.008 | 修正被误分类为通用实体的中文电话号码 |
| Validate | +0.031 | 移除无效格式（精确率提升最大） |
| Filter | +0.024 | 移除被误标为人名的代词、医学术语 |
| Normalize | +0.012 | 去除前缀，提高边界准确性 |
| Email/IP Regex | +0.018 | 捕获 NER 模型遗漏的邮箱/IP |
| Threshold | +0.015 | 按类型的置信度过滤减少噪声 |
| Dedup | +0.006 | 移除冗余的重叠跨度 |
| Merge | +0.009 | 合并被拆分的人名和地址 |
| **总计** | **+0.123** | 原始模型 F1: 0.779 → 最终 F1: 0.902 |

流水线提升了约 12 个点的 F1。验证和过滤贡献最大——它们移除了模型高置信度但错误的预测，这些预测严重损害精确率。

## INT8 vs FP32 精度对比

我们提供 INT8 量化编码器（511MB vs 1.1GB FP32）。精度影响极小：

| 模型 | F1 | 延迟 (M-series) | 延迟 (Xeon 4-core) |
|------|----|-----------------|---------------------|
| FP32 encoder | 0.904 | ~150ms | ~350ms |
| INT8 encoder | 0.902 | ~150ms | ~250ms |

INT8 在 x86 CPU 上带来显著加速（得益于原生 INT8 VNNI 指令），F1 仅损失 0.002。在 ARM（Apple Silicon）上，由于缺少专用 INT8 加速硬件，速度和精度差异均可忽略。

## 与替代方案的对比

我们在多语言测试集上与常见 PII 检测方案进行了对比：

| 方案 | F1 (EN) | F1 (Multi) | 延迟 | 需要 GPU |
|------|---------|------------|------|----------|
| Regex-only | 0.62 | 0.41 | <5ms | No |
| spaCy NER | 0.78 | 0.54 | ~50ms | No |
| Presidio (Microsoft) | 0.82 | 0.61 | ~100ms | No |
| GPT-4 (prompted) | 0.91 | 0.85 | ~2000ms | Cloud API |
| **PII Engineer** | **0.93** | **0.90** | **~150ms** | **No** |

PII Engineer 达到 GPT-4 级别的精度，延迟低 13 倍，完全本地运行，无需将敏感数据发送至外部 API。

## 错误分析

我们对剩余错误（F1 与 1.0 的差距）进行了分类：

- **38% 边界错误** — 实体被检测到但跨度过长或过短
- **27% 漏检** — 实体完全未被检测到（通常是歧义上下文中低置信度的人名）
- **21% 误报** — 非 PII 被标记为 PII（产品名被当作人名，订单号被当作证件号）
- **14% 标签混淆** — 实体被检测到但类型错误（passport_number vs government_id）

边界错误占比最大且最难修复——需要模型学习更精确的跨度边界，我们正在 v2.2 训练中通过改进标注指南来解决此问题。
