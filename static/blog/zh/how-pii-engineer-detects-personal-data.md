## 挑战

在多语言文本中检测个人身份信息（PII）远比看上去困难。英文人名与中文、马来文或越南文的人名遵循不同的模式。各国的政府证件号码格式各异——新加坡的 NRIC、印度尼西亚的 NIK、印度的 Aadhaar、越南的 CCCD 格式截然不同。电话号码、地址和日期在不同文化中的书写方式也不一样。

大多数 PII 检测工具以英文为主，其他语言只是后续添加的补充。我们需要的是将 13+ 种语言全部视为一等公民的解决方案。

## 架构概览

PII Engineer 采用双模型方案：

1. **GLiNER2 Multi-NER** — 基于 mDeBERTa-v3-base（约 2.8 亿参数）的跨度式 NER 模型，使用 LoRA 微调以检测所有支持语言中的 PII
2. **Chinese NER** — 基于 BERT 的序列标注分类器，使用 BIO 标注方式，专门针对中文文本训练，因为中日韩字符需要不同的分词处理

系统会检测输入中的 CJK 字符，当存在中文文本时自动路由至两个模型。对于非 CJK 文本，仅运行 GLiNER2 模型。

## GLiNER2：跨度式 NER

与传统的序列标注（BIO 标注）不同，GLiNER2 采用跨度式方法。它不是对每个 token 进行分类，而是评估候选文本跨度并与实体类型嵌入进行匹配评分。

该模型由 5 个 ONNX 组件构成：

| 组件 | 大小 | 功能 |
|------|------|------|
| encoder | 511MB (INT8) | mDeBERTa-v3-base token 编码器 |
| span_rep | 63MB | 跨度表示层 |
| count_embed | 41MB | 计数嵌入，用于跨度评分 |
| count_pred | 4.6MB | 计数预测头 |
| classifier | 4.5MB | 最终分类头 |

我们提供 INT8 量化编码器（511MB vs 1.1GB FP32），在 x86 CPU 上可获得约 15-20% 的推理加速，精度损失可忽略不计。

## 8 阶段流水线

原始 NER 输出存在噪声。模型可能将"Dr."标记为人名、检测到无效电话号码或返回重叠实体。我们的后处理流水线负责清理这些问题：

### 1. 重分类

中文电话号码常出现在"电话"或"手机"等标记词附近。如果一个通用实体出现在这些标记词附近，我们将其重分类为 `phone_number`。

### 2. 格式验证

每种实体类型都有格式验证规则。电话号码必须包含足够的数字且不含字母。政府证件号需达到最小长度并包含字母数字字符。护照号码不能仅由数字组成。不符合格式的候选项会被拒绝。

### 3. 过滤

我们维护了一个元词汇表——包括代词（"我"、"你"、"她"）、亲属称谓（"妈妈"、"丈夫"）、医学术语（"医生"、"病人"）以及标签词本身（"姓名"、"电话"）。匹配这些词汇的实体会被过滤掉。

### 4. 规范化

去除人名中的上下文前缀，如"Patient"、"Dr."、"Mr."。"Patient Sarah Lim" 变为 "Sarah Lim"。

### 5. 邮箱/IP 检测

使用正则表达式检测电子邮件地址和 IPv4 地址。这些模式结构性极强，正则表达式比 NER 捕获更可靠。

### 6. 置信度阈值

按标签设置不同的置信度阈值。人名使用较低阈值（0.25），因为其形式多样；电话号码使用较高阈值（0.30），因为模型对结构化模式更有把握。

### 7. 去重

相同标签的重叠实体会被去重——较长的跨度优先保留。不同标签的重叠实体则同时保留。

### 8. 合并

相同标签且间隔不超过 3 个字符的相邻实体会被合并。"John" + " " + "Doe" 合并为 "John Doe"。

## 延迟

在搭载 FP32 编码器的 MacBook M 系列芯片上，典型推理延迟约 150ms。在使用 INT8 编码器的 4 核 Xeon 服务器上，约 250ms。整个流水线运行在 CPU 上——无需 GPU。

服务器首次运行时自动从 HuggingFace 下载模型，预热 ONNX 会话，并将模型权重锁定在内存中以防止被换出。

## 立即体验

PII Engineer 以 AGPL-3.0 协议开源。一条命令即可启动：

```
cargo build --release --package pii-engineer-server
cargo run --release --package pii-engineer-server
# 模型自动下载 — http://localhost:8000
```
